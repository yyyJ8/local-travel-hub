## P2 · 一句话结论

> **模块化单体起步 → 读写分离扛量 → 垂直拆分扩容 → 单元化多活保稳定**

- 四步走，不一步到位
- 每一步只解决当前瓶颈
- 按瓶颈升级，不是按时间升级

> 🎤 一句话概括整场汇报：不要一步到位，每一步只为当前瓶颈付费。

---

## P3 · 判断依据 ①：读多写少

- 1000 万 DAU ≈ **2~4 亿请求/天**
- 平均 **3500 QPS**，峰值 **2~3 万 QPS**
- 下单只有 20~30 万单/天 → 写路径平均 **仅 3 TPS**
- 读写比约 **100 : 1**

**结论**：读靠 CDN + 缓存 + 搜索引擎扛；写靠事务 + 幂等 + 对账保正确。

> 🎤 先算数，再选型。读路径要扛几万 QPS，写路径只有几 TPS——所以性能投入的九成都该花在读上。

---

## P4 · 判断依据 ②：写路径拼的不是吞吐，是正确性

三件事决定平台能否商用：

| 必须做到 | 技术手段 |
| --- | --- |
| 库存不超卖 | Redis Lua 原子预占 → 数据库乐观锁 → 日终对账 |
| 价格不错 | 展示价与结算价同源下发，写订单快照 |
| 订单不重复 | 幂等键 + 唯一约束 |

> 🎤 下单量不大，但每一次都必须是对的。这三件事错了就是资金损失和客诉。

---

## P5 · 判断依据 ③：架构匹配团队规模

- **康威定律**：组织架构决定系统架构
- 携程经验值：**人均应用 ≤3 个、调用层级 ≤5 层、严禁循环依赖**
- 治理收益：核心应用调用量 **↓73%**，查询引擎 **QPS 8 万 → 24 万**
- 服务不是越小越好，是"**合适的大小**"

> 🎤 30 人的团队硬上微服务，收益（独立迭代）拿不到，分布式复杂度全付了。

---

## P6 · 技术路线：四步走

| 阶段 | 架构形态 | 支撑量级 | **触发信号** |
| --- | --- | --- | --- |
| 1 | 模块化单体 + MySQL + Redis + CDN | 10 万 DAU | 需要真实注册、下单、持久化 |
| 2 | 垂直拆分 5~8 个服务 + 读写分离 + 搜索 + MQ | 100 万 DAU | 单库写入打满、团队开发互相阻塞 |
| 3 | 微服务 + 分库分表 + K8s 多可用区 + 单元化 | 1000 万 DAU | 单机房容量或容灾不达标 |

> 🎤 请看最后一列：不是"到点了该升级"，而是"出现瓶颈才升级"。

## P7 · 选型总览（一）：接入与业务

| 层 | 选型 | 一句话理由 |
| --- | --- | --- |
| 客户端 | 原生 App + 小程序 + H5/PC | 小程序低成本拉新，多端共用聚合接口 |
| 图片静态 | **对象存储 + CDN** | OTA 最大带宽成本项，命中率决定账单 |
| 网关 | APISIX / Spring Cloud Gateway | 统一鉴权·限流·灰度，不各写一套 |
| 服务框架 | **Java + Spring Cloud Alibaba**；边缘用 Go | 交易资金域 Java 生态最成熟，Go 扛高吞吐边缘 |
| 服务治理 | Nacos + Sentinel + 链路追踪 | 治理的收益远大于堆机器 |

> 🎤 选型的核心不是"哪个技术新"，而是"哪个生态最成熟、团队最容易承接"。

---

## P8 · 选型总览（二）：数据与基础设施

| 层 | 选型 | 取舍点 |
| --- | --- | --- |
| 缓存 | Redis Cluster + 本地多级缓存 | 挡热点，扣减用 Lua 保原子 |
| 消息 | RocketMQ / Kafka | 削峰、异步解耦、最终一致 |
| 搜索 | Elasticsearch（含附近搜索） | POI/酒店检索是核心体验 |
| 主库 | MySQL 分库分表 **或** TiDB / OceanBase | **团队有没有分布式数据库运维能力** |
| 分析 | ClickHouse / Doris + Flink | 看板、榜单、实时风控特征 |
| 部署运维 | K8s 多可用区 + CI/CD + 可观测 | 无状态才能弹性扩缩容与回滚 |

> 🎤 主库这个二选一最有代表性：不是技术先进性问题，是运维能力问题。

---

## P9 · 三个必答问题

| 问题 | 答案要点 |
| --- | --- |
| **怎么不超卖？** | Redis Lua 预占 + 数据库乐观锁 + 日终对账；热点房源用"预扣 + 分段库存 + 队列串行化"。扣减要原子、释放要及时、差异要对账 |
| **缓存与库不一致？** | 分级：库存/支付/券不靠缓存判正确性；评价/榜单用 Cache Aside + 延迟双删 + binlog 刷新 |
| **多机房冲突？** | **单元化**：用户按 UID 路由到固定单元，单元内闭环，同一份数据不被两个机房同写；容灾必须常态化演练 |

> 🎤 如果只被问三个问题，大概率就是这三个——建议背下来。

---

## P10 · 收尾口径

1. **当前是原型**：本机、内存、不持久化；以上是生产演进目标
2. **顺序不能乱**：先持久化与无状态化，再谈拆分与多活
3. **复杂度就是成本**：月基础设施数百万元量级，**人力成本通常更高**

> 🎤 所以过度设计不是技术问题——它就是直接烧钱。
