## P2 · 一句话定位

> 一个**仿大众点评 + 携程**的本地生活旅行平台：
> 浏览搜索 → 筛选决策 → 预订下单 → 订单管理，并按角色开放商家后台与管理后台。

- 双业务形态：本地生活 + 旅行住宿
- 一条主流程闭环：看 → 选 → 订 → 管
- 三个角色：普通用户 / 商家 / 管理员

> 🎤 一句话说清定位：它把大众点评和携程两条业务线放在一个系统里，走通一条完整的交易闭环。

## P3 · 五大功能模块

| 模块 | 对标 | 核心能力 |
| --- | --- | --- |
| 首页 | — | 轮播推荐、分类入口、推荐门店/酒店、关键词搜索 |
| 本地生活 | 大众点评 | 门店列表（城市/品类/评分/人均筛选 + 排序）、详情（营业时间、地址、团购套餐、用户评论） |
| 旅行住宿 | 携程 | 酒店列表（城市/星级/价格/设施筛选 + 日历选入住退房）、详情（房型房价、酒店评价） |
| 预约下单 | — | 选套餐/房型 → 填姓名手机号 → 选时间 → 提交 |
| 个人中心 + 双后台 | — | 我的订单与取消；商家后台；管理后台 |

> 🎤 五大模块覆盖了"浏览—决策—交易—管理"的完整链路，不是一堆互不相干的页面。

## P4 · 三个角色，三种视角

| 角色 | 能看到什么 | 演示价值 |
| --- | --- | --- |
| 普通用户 `demo` / `lisi` | 只有**自己的**订单 | 换账号登录 → 订单不同，证明**数据归属隔离** |
| 商家 `shangjia` | 只有**自己名下门店**的订单 | 只看得到 S001，证明**商户级隔离** |
| 管理员 `admin` | 全平台概览、用户、订单；可停用账号 | 停用某账号 → **立即登录不上、原会话立即失效** |

> 🎤 权限不是嘴上说的——换三个账号登录一次，隔离效果当场可见。

## P5 · 系统规模（不是空壳）

- 功能模块 **5** 个，接口 **21** 个
- 门店 **20** 家（成都 12 / 重庆 4 / 西安 4）、酒店 **16** 家
- 套餐 **4** 个/店、房型 **4** 种/酒店、评论 **≥10** 条/对象
- 预置订单 **3** 条、演示账号 **4** 个
- 图片 **39** 张本地化存储 → **断网也能演示**
- 自检 **205 项全通过**（数据层 33 + 认证权限 41 + 接口 45 + 端到端 44 + 前端 42）

> 🎤 这些数字说明两件事：数据量足够演出筛选排序的效果，质量有自检保证。

## P6 · 现场能演示什么（四条动线）

1. **搜索决策**：搜"火锅" → 结果页分区展示门店 + 酒店
2. **筛选排序**：切城市/品类/评分/人均 → 列表条数肉眼可见地变
3. **日历联动**：酒店选入住退房 2 晚 → 总价自动 = 单价 × 2
4. **交易闭环**：下单 → 个人中心立即可见 → 取消 → 状态变"已取消"
5. **权限三连**：换三个账号登录，数据范围各不同

> 🎤 每一条都能独立演示，任意一条出问题都不影响其余演示。

## P7 · 五视图法：是什么

> 用**五个视角**描述同一套系统，避免"只从一个角度讲，说不清全部"。

| 视图 | 回答的问题 |
| --- | --- |
| 逻辑视图 | 做什么（有哪些业务能力、怎么分层） |
| 开发视图 | 代码怎么组织、怎么复用 |
| 数据视图 | 存什么、怎么关联、存在哪里 |
| 运行视图 | 一次请求怎么跑完、并发与鉴权怎么处理 |
| 物理视图 | 装在哪、怎么扩 |

> 🎤 一句话：三个静态视角（逻辑/开发/数据）+ 两个动态视角（运行/物理），合起来才是完整的架构描述。

## P8 · 五视图在本项目的落点（一）

| 视图 | 本项目的对应证据 |
| --- | --- |
| **逻辑视图** | 5 个业务域（首页/本地生活/旅行住宿/订单/账号权限）+ 三层分层：Vue 页面 → FastAPI 路由 → 内存 store，鉴权为横切层 |
| **开发视图** | 前后端两工程；前端 `router / api / components / views / composables`，后端 `main / api / models / data / core`；**8 个公共组件复用**（导航、底部栏、星级、弹窗、两类卡片、封面图、骨架屏） |
| **数据视图** | 对象：Shop、Package、Hotel、RoomType、Comment、Order、Banner、Category、User、Session；关系：门店 1—N 套餐/评论、酒店 1—N 房型/评价、订单 N—1 目标与商品 |

> 🎤 每个视图我都能指到具体的代码位置——不是画在图上的空架构。

## P9 · 五视图在本项目的落点（二）

| 视图 | 本项目的对应证据 |
| --- | --- |
| **运行视图** | 浏览器 SPA → Axios(`/api`) → Vite 代理 → Uvicorn/FastAPI → store；令牌链路：登录发 token → localStorage → 路由守卫 → 请求带 `Authorization: Bearer` → **401 未登录 / 403 越权** |
| **物理视图** | 原型：本机双进程（前端 5173 / 后端 8000），物理架构即本地运行架构；生产演进：CDN + 负载均衡 + 服务多实例 + 数据库读写分离/分片 |

> 🎤 运行视图讲的是"一次请求怎么跑完"，物理视图讲的是"装在哪、以后怎么扩"。

---

## P10 · 总纲与衔接

**总纲**：逻辑 / 开发 / 数据 = 静态设计；运行 / 物理 = 动态与部署。五视图合起来覆盖"业务能力 → 代码 → 数据 → 运行 → 部署"的完整链路。

**与技术路线的衔接**（被问"以后怎么扩"时用）：

| 演进动作 | 改动哪个视图 |
| --- | --- |
| 数据落库、会话外置（阶段 1） | **数据视图 + 运行视图** |
| 垂直拆分为多个服务（阶段 2） | **逻辑视图 + 开发视图** |
| 多可用区、单元化多活（阶段 3） | **物理视图** |

> 🎤 所以五视图不只是一份文档——它是我们描述"现在什么样、以后怎么变"的统一语言。
